# ADR-023 — OpenRouter Is the Production Model Gateway

**Status:** Accepted · **Date:** 2026-09 · **Scope:** Model abstraction / infrastructure
**Supersedes:** ADR-004 (LiteLLM as the model gateway)

## Context

ADR-004 chose **LiteLLM** as the self-hosted gateway, with Ollama as a zero-cost
provider. The reasoning that produced it still holds and is reaffirmed here:

- domain code must never call a vendor SDK directly — everything goes through one
  provider chain, so routing, fallback, cost tracking and authority checks live in
  one place;
- the platform must be multi-vendor without a code change per vendor;
- a local, free path must exist so the product runs with zero model cost.

What changed is the *operational* half of that decision. The platform never
deployed a LiteLLM gateway: there is no instance in any environment, and the
"self-hosted proxy" it described is a service somebody has to run, upgrade, secure
and monitor. Meanwhile the deployment that actually exists — API on a host, one or
two provider keys as environment variables — gets no benefit from an extra hop,
and the chain order it did have was ambiguous: with several credentials present,
which provider served a request depended on the workspace's key set rather than on
a stated decision. The order also lived in more than one place, so it could drift.

OpenRouter fills the same role ADR-004 wanted a gateway for — one key fronting many
vendors, with token and cost metadata — as a service rather than as infrastructure
we operate.

## Decision

**OpenRouter is the primary model provider.** NVIDIA NIM is the documented first
fallback. LiteLLM and Ollama are **development-only** and always tried last.

| # | Provider | Role | Credentials |
|---|----------|------|-------------|
| 1 | OpenRouter | **Primary** — one key fronts many vendors | `OPENROUTER_API_KEY` / `OPENROUTER_API_KEYS` |
| 2 | NVIDIA NIM | First fallback, when a workspace holds NIM credentials | `NVIDIA_API_KEY` / `NVIDIA_API_KEYS` |
| 3 | LiteLLM | Development gateway only | `LITELLM_BASE_URL` (+ `LITELLM_MASTER_KEY`) |
| 4 | Ollama | Development local models; no auth | `OLLAMA_BASE_URL`, `OLLAMA_MODEL` |

1. **The order is declared once**, as `PROVIDER_PRIORITY` in
   `apps/api/src/services/model-router.ts`. `ModelRouter.getProviderChain()` and
   `buildProviderChain()` (the direct HTTP chain behind `chatCompletion`) both
   derive from it; no other file may carry its own copy. `isDevelopmentProvider()`
   marks `litellm`/`ollama`.
2. **A pinned model id is honoured exactly.** `openai/gpt-4o-mini` or
   `anthropic/claude-…` reaches the vendor that serves it, so "run this task on
   that model" means what it says.
3. **Unpinned routing is deterministic.** The default destination is one
   predictable path instead of whichever credentials a deployment happens to hold.
4. **Providers are configurations, not integrations.** A provider with no
   credentials is absent from the chain rather than failing at call time; adding
   one means adding an adapter, not touching domain code.
5. **A workspace with no OpenRouter key still works.** The chain falls back to NIM
   and then to the development providers, and a deployment with no provider at all
   degrades to structured output rather than failing the task.

ADR-004's central rule — *domain code never calls provider SDKs directly* — is
retained unchanged and is the reason this is an amendment rather than a reversal.

## Alternatives considered

- **Keep LiteLLM primary.** Rejected: it makes an unowned, un-deployed service the
  default path for every production request, and its benefit (one interface for
  many vendors) is delivered by OpenRouter without the hop.
- **NVIDIA NIM primary.** Rejected: a narrower catalogue that cannot serve
  arbitrary pinned vendor models, which is the property the routing design depends
  on. It is a genuinely useful second attempt and stays as the first fallback.
- **Per-vendor SDKs behind a thin wrapper.** Rejected: reintroduces per-vendor
  code paths in domain-adjacent services and loses the single cost/trace boundary.
- **Make OpenRouter optional and leave the order unspecified.** Rejected: an
  unspecified default is what produced the drift this ADR closes.

## Consequences

- **LiteLLM is not removed.** It remains a supported development gateway, so an
  offline or air-gapped workspace keeps working; it is simply never the production
  default.
- **A stray local URL cannot decide a production request.** Because development
  providers are last, a misconfigured `LITELLM_BASE_URL` can serve local traffic
  without ever leading the chain.
- **Fallback is real, not decorative.** Losing OpenRouter mid-flight fails over to
  NIM through the existing circuit breaker and retry logic; the chain is the same
  code path either way.
- **Tests pin the order, not the prose.** `apps/api/test/model-router.test.ts`
  asserts `PROVIDER_PRIORITY` exactly, that `getProviderChain()`'s first entry is
  OpenRouter, that a fully configured chain matches the declaration in order, and
  that only `litellm`/`ollama` report as development providers. A reordering
  cannot land silently.
- **Deployment docs and templates must agree.** `.env.example` files and the
  routing docs list the providers in this order; a mismatch is a documentation bug
  (docs/58).
- **Cost attribution is per-provider.** OpenRouter's usage metadata is what
  `llm_traces` and model-performance routing read, so "which model served this" is
  measured rather than assumed.
